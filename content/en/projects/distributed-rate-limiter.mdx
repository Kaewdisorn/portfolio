## Overview

Designed and led implementation of a distributed rate limiting system for a multi-tenant API platform. The system processes millions of decisions per second across multiple geographic regions, achieving sub-3ms p99 latency with 99.97% enforcement accuracy. This replaced a single-Redis counter that had become both a reliability risk and a cross-region bottleneck.

## Problem

Two problems converged as the platform expanded across regions.

The existing single-Redis rate limiter was a single point of failure. When Redis was unavailable, the entire enforcement layer dropped — all traffic passed unchecked. More critically, once we deployed to multiple regions, each region enforced limits independently. A tenant could hit the limit in `us-east` while consuming freely in `eu-west`, making global limits meaningless.

Simultaneously, one partner's batch job was generating 30,000 requests per minute during business hours, consuming 60% of API capacity and pushing p99 latency for other tenants above 800ms. The underlying cause was structural: the system had no mechanism to detect or respond to sustained abuse.

## My Role

Tech lead responsible for architecture design and core Go implementation. Worked with a team of three engineers over six months, delivering in three staged rollouts. Designed the integration with the existing Nginx-based infrastructure and wrote the runbook for the Redis Cluster failover procedure.

## Architecture

The system is a two-tier design with regional local decisions as the default path.

**Local tier**: Each region has an independent Redis Cluster. A Go sidecar proxy runs alongside each service pod and intercepts all inbound requests. Token bucket operations execute atomically via a Lua script on Redis. This path adds under 1ms to request latency.

**Global sync tier**: A gRPC stream connects regional agents. Every 5 seconds, each region reports token consumption to a lightweight aggregator, which redistributes adjusted per-region budgets when a tenant approaches the global limit. Regions act independently between sync cycles.

## Key Decisions

### Token Bucket Algorithm

The sliding window algorithm offers exact per-second accuracy but stores one timestamp entry per request. At 1 million requests per minute across thousands of tenants, memory usage becomes unpredictable. Token bucket reduces state to two integers per tenant regardless of traffic volume. The tradeoff — short burst allowance — was acceptable because real API clients send bursty traffic naturally, and the product team agreed the burst window of one second was reasonable.

### Eventually Consistent Global Sync

Synchronous global enforcement requires a round-trip between regions on every decision. With 80ms inter-region RTT, this adds latency that breaks the 5ms SLO. The 5-second sync interval was chosen after analyzing partner traffic patterns: every confirmed abuse case exceeded limits for at least 30 seconds. The window allows a short burst to slip through during a sync cycle, but sustained overuse is caught within two cycles.

### Unix Domain Socket Communication

Initial benchmarking showed TCP loopback between the sidecar and the service pod added 0.4ms per request due to kernel TCP stack processing. Switching to Unix domain sockets reduced this to 0.06ms — below measurement noise. For a system where the total latency budget is 3ms, this 0.34ms saving was significant.

## Challenges and Solutions

### Redis Cluster Slot Rebalancing

Redis Cluster migrates slots between nodes during scaling operations, returning MOVED responses for keys on the old node. Our initial client treated MOVED as an error and failed the rate limit check, causing those requests to bypass enforcement entirely. The fix involved MOVED-aware retry logic that follows the redirect immediately, plus an in-memory token bucket fallback for the affected key range while migration is in progress. Fallback activates automatically and deactivates when the slot stabilizes. Measured accuracy loss during fallback: 0.01%.

### Lua Script Latency Spikes

Under high load, Lua script execution time varied from 0.3ms to 12ms depending on Redis server CPU state. Redis executes scripts atomically, so a slow script blocks all other commands. We refactored the script to only cover the minimum atomic section — the compare-and-decrement — and moved the refill calculation to the application side. The script went from 18 lines to 7 lines. Worst-case execution time dropped to 1.2ms. We also added a 2ms script timeout with fail-open fallback to protect the latency SLO.

## Impact

- p99 rate limit decision latency under 3ms — 67% faster than single-Redis baseline
- Enforcement accuracy 99.97% — false rejection rate below 0.03%
- Zero enforcement downtime on single Redis node failure — 99.99% availability maintained
- Noisy neighbor incidents from partner API abuse fully eliminated after rollout
- Five partner tenants operate under individual rate limit policies with no ongoing operational overhead
