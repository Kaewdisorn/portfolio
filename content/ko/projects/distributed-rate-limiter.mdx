## 개요

멀티 리전 환경에서 운영되는 API 플랫폼에서 테넌트 간 공정한 리소스 배분을 보장하는 분산 속도 제한 시스템을 설계하고 구현했습니다. 기존 단일 Redis 카운터 방식의 한계를 극복하고, 3ms 이하의 p99 레이턴시와 99.97%의 판단 정확도를 달성했습니다.

## 문제

서비스가 멀티 리전으로 확장되면서 두 가지 문제가 동시에 발생했습니다.

첫째, 기존 단일 Redis 인스턴스는 싱글 포인트 오브 페일러였고 리전이 늘어나도 확장할 수 없었습니다. 둘째, 특정 파트너사가 분당 수만 건의 요청을 보내 다른 테넌트의 응답 시간이 3배 이상 느려지는 노이지 네이버 문제가 프로덕션에서 반복되었습니다.

속도 제한을 리전마다 따로 두면 글로벌 한도를 초과해도 감지할 수 없고, 중앙 집중식으로 두면 리전 간 RTT가 레이턴시 SLO를 위협합니다. 이 딜레마를 해결하는 것이 핵심 과제였습니다.

## 역할

테크 리드로서 아키텍처 설계와 핵심 Go 구현을 담당했습니다. 3명의 팀원과 함께 6개월에 걸쳐 단계적으로 배포했으며, 기존 Nginx 기반 인프라와의 통합을 직접 설계했습니다.

## 아키텍처

리전 로컬 판단을 기본으로 하는 2-티어 구조를 채택했습니다.

**로컬 티어**: 각 리전에 Redis Cluster가 독립적으로 운영됩니다. Go 사이드카 프록시가 각 서비스 파드 옆에 배포되어 모든 인바운드 요청을 인터셉트하고, Lua 스크립트로 토큰 버킷 연산을 원자적으로 실행합니다.

**글로벌 동기화**: gRPC 스트림을 통해 5초마다 리전 간 토큰 소비량을 집계합니다. 글로벌 한도에 근접하면 각 리전의 로컬 한도를 동적으로 조정합니다.

## 핵심 결정

### 토큰 버킷 알고리즘 선택

슬라이딩 윈도우는 밀리초 단위의 정확도를 제공하지만, 요청마다 타임스탬프를 저장해야 하므로 초당 수만 건의 요청에서 메모리 사용량이 예측 불가능하게 증가합니다. 토큰 버킷은 두 개의 정수값만 관리하므로 테넌트 수가 늘어도 메모리 사용량이 선형적으로 예측 가능합니다. 단기 버스트를 허용하는 특성이 실제 API 트래픽 패턴과도 잘 맞았습니다.

### Eventually Consistent 글로벌 동기화

완전 동기 방식은 리전 간 RTT를 레이턴시에 직접 추가합니다. 5초 동기화 주기를 선택한 이유는 대부분의 남용 패턴이 수십 초 이상 지속되기 때문입니다. 짧은 버스트는 각 리전에서 독립적으로 허용하고, 지속적인 초과만 글로벌하게 제한하는 방식은 실제 요구사항에 충분했습니다.

### Unix 도메인 소켓 통신

사이드카와 서비스 간 통신에 TCP 대신 Unix 도메인 소켓을 사용했습니다. 동일 파드 내 통신에서 TCP 스택 오버헤드를 제거해 소켓 통신 레이턴시를 0.1ms 미만으로 낮췄습니다.

## 도전과 해결

### Redis Cluster 리밸런싱 중 오류

MOVED 응답 처리에 재시도 로직을 추가하고, 리밸런싱 감지 시 해당 키 범위를 인메모리 카운터로 폴백했습니다. 리밸런싱 완료 후 자동으로 Redis로 복귀하며, 폴백 기간 중 정확도 손실은 측정 결과 0.01% 미만이었습니다.

### Lua 스크립트 블로킹

원자 연산이 필요한 부분만 Lua로 유지하고 나머지는 파이프라인으로 처리했습니다. 타임아웃 시 fail-open 정책을 적용해 레이턴시 SLO를 방어합니다. 실제 타임아웃 발생률은 프로덕션에서 0.001% 미만입니다.

## 성과

- p99 속도 제한 판단 레이턴시 3ms 이하 달성 (단일 Redis 대비 67% 개선)
- 속도 제한 정확도 99.97% — 허용해야 할 요청을 거부하는 오탐률 0.03% 미만
- Redis 노드 1개 장애 시에도 판단 중단 없이 가용성 99.99% 유지
- 파트너 API 남용으로 인한 전체 서비스 응답 지연 이슈 완전 해소
- 멀티 테넌트 5개 파트너사에 개별 한도 정책 셀프서비스 적용
